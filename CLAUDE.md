## What we are building
One platform integrated with the existing **FAZL APP** with three modules:
1. **Ride booking**: Uber/Careem-style. Passenger books, driver accepts, live GPS tracking, ratings, history.
2. **FAZL order/delivery tracking**: a FAZL order can be tracked live (delivery person, vehicle, route, ETA, status timeline).
3. **Parking discovery**: map of nearby parking with total/available/occupied spaces, pricing, hours, navigation. Reservation/payment is a future phase.

Source spec: `FAZL Drivedocx.pdf` (34 sections, in `~/Documents/fazl`, next to the repos). Follow its Section 32: confirm flows, API, DB and business rules before building each module; anything outside agreed scope is a change request.

## Design principle: integration-first (user requirement, 2026-09-21)
The platform must stay flexible so **any external system or new module can be integrated through the API**. Rules to follow when building anything:
1. **Modular monolith.** Each domain (auth/users, drivers, parking, rides, order-tracking, ...) is a self-contained Nest module: own controller, service, DTOs. Other modules use its exported service, never its Prisma tables. Adding a module = adding a folder and one import in `AppModule`.
2. **Two ways in, one set of rules.** User apps use JWT (roles). External systems (FAZL app, parking sensors/software, partners) use **API keys with scopes** (e.g. `parking:write`, `orders:read`), hashed at rest, revocable, with `lastUsedAt` and per-key rate limits. Admin endpoints create/revoke keys. A guard accepts either a JWT or an API key on the routes meant for both.
3. **Provider adapters for everything external.** Storage (`StorageService`), SMS (`SmsProvider`) already work this way. Parking availability (manual now, sensors later) and FAZL order status will too. New integration = new adapter class, no change to business logic.
4. **Stable, documented contract.** Versioned (`/api/v1`), Swagger/OpenAPI is the source of truth (partners can generate clients from `/docs-json`), consistent pagination and error shape, `Idempotency-Key` on external POSTs that create things.
5. **Events out.** Important state changes (driver approved, parking availability changed, order status changed) should be emitted as domain events so outbound webhooks or push notifications can subscribe without touching the module that raised them.
6. **Config over code.** Statuses, thresholds (e.g. parking "Limited"), fare rules, required documents live in config/DB where the business is likely to change them.

## Ride module spec (confirmed by the user 2026-09-21, defaults noted)
- **Vehicle categories (user decision 2026-09-21): only `bike` and `car`**, because those are the only two that run in Pakistan. The passenger picks which one; a bike costs less than a car. The mockup's Economy/Comfort/XL rows are replaced by Bike and Car. The driver's license is the same document for both, so there is no extra paper for bikes. A driver can register both a bike and a car and picks one when going online. Categories are still a Postgres enum, so adding one later needs a migration (an admin-editable table was suggested but not chosen yet).
- **Fare:** per category (`bike`, `car`): base + per-km + per-minute, with a minimum fare, all in PKR whole rupees, stored in `fare_configs` and editable through admin endpoints. Seeded values are placeholders the business must set. Cash only. Final fare is computed at completion from the distance actually driven and the real duration.
- **Matching:** on request, offer the ride to the nearest N (default 5) online, approved drivers of the requested category within a radius (default 3 km); the first to accept wins (atomic update on the ride). If nobody accepts, the radius grows on a timer; the request expires after ~2 minutes.
- **Lifecycle:** `requested -> accepted -> arrived -> started -> completed`, or `cancelled` / `expired`. One active ride per passenger and per driver. **No cancellation fee** (user decision 2026-09-21): rides are cash only, so nothing can be collected. The passenger can cancel any time before the ride starts; once `started` it can only be ended by the driver. If the driver cancels before starting, the ride goes back to `requested` and is re-offered to other drivers (the driver who backed out is not offered it again).
- **Realtime:** Socket.IO gateway (JWT in the handshake) for offers, ride updates and driver location; every action also exists as REST so the app can poll. Live driver locations sit in Postgres/PostGIS behind a `DriverLocationStore` adapter; Redis can replace it later without touching ride logic.
- **Routing/ETA:** behind a `RoutingProvider` adapter. Now a straight-line estimate with a detour factor; swap in Google Directions when a key exists.
- **Ratings:** both directions, 1-5 stars + optional comment, one per rater per ride.
- Sub-milestones: B1 fares + estimate, B2 driver presence + nearby, B3 request/offers/accept + expiry sweeper, B4 lifecycle + fare calculation + distance tracking, B5 ratings + history + admin rides, B6 Socket.IO, B7 push (FCM).

## Built so far (customer + driver foundation)
All routes are under `/api/v1`, Swagger at `/docs`.
- `auth`: `POST auth/otp/request`, `auth/otp/verify` (first verify registers the user as `customer`), `auth/refresh` (rotating refresh tokens, replay of a revoked token revokes all), `auth/logout`. OTP is HMAC-hashed, 5 min TTL, 60 s resend gap, 5 attempts. SMS goes through the abstract `SmsProvider`; only `ConsoleSmsProvider` exists (prints the OTP in the server log). Phones are normalized to `+923XXXXXXXXX`.
- `users`: `GET/PATCH users/me` (returns roles and driver application status).
- `drivers`: `POST drivers/apply` (cnic + license + first vehicle, re-apply allowed after rejection), `GET drivers/me`, `POST drivers/me/vehicles` (approved drivers only).
- `admin` (role admin/super_admin): list users, list/get drivers, approve/reject driver (approve grants the `driver` role, reject removes it), approve/reject vehicle.
- Documents: `POST drivers/me/documents` (multipart `file` + `type` [+ `vehicleId` for `vehicle_registration`]; JPEG/PNG/WebP/PDF by magic bytes, max 5 MB; same type again replaces the old file), `GET drivers/me/documents`. Admin `GET admin/drivers/:id` returns documents with 10-minute signed URLs. Approve/reject never call storage. Re-applying after a rejection deletes the old vehicles' registration files.
- Roles are read from the DB on each request (JwtStrategy), so approval/block is immediate.
- First super admin: put the phone in `SUPER_ADMIN_PHONES` (env); it gets `super_admin` on its next OTP login.
- Gotcha: `@nestjs/passport` 12 with Nest 12 fails to resolve `AuthModuleOptions` in `JwtAuthGuard` unless `PassportModule.register(...)` is used (done in `AuthModule`, exported to feature modules).
- Tests: `npm test` (phone normalizer), `npm run test:e2e` (validation + 401 guards, no DB needed). The full flow (OTP, apply, duplicate CNIC/plate, approve/reject, re-apply, refresh rotation and replay, admin routes) was verified by hand against the local DB on 2026-09-21; that script is not in the repo. Prisma 7 + pg adapter puts the violated constraint name in `error.meta.driverAdapterError.cause.constraint.index`.
- Auth throttle: `otp/request` is limited to 5/min per IP, so scripted tests need pauses.
- **`DEV_OTP_BYPASS=true`** (2026-09-22): any phone logs in with a fixed code (`DEV_OTP_CODE`, default `123456`), so someone testing the app (a client, another phone) can sign in without reading the server log. Off by default, every use logged as a warning, never set on a server real users reach.
- **`DEV_AUTO_APPROVE_DRIVERS=true`** (2026-09-22): same spirit as `DEV_OTP_BYPASS`, for the other slow step - waiting for a human admin. A driver still goes through the real "Become a Driver" screens (apply, upload every required document); the moment `DriverRequirementsService` says nothing is missing, `DriverApprovalService.maybeAutoApprove()` approves the driver profile and its vehicles and grants the `driver` role, exactly as `POST admin/drivers/:id/approve` would (that endpoint now delegates to the same `DriverApprovalService.approve()`, so there is one place that decides what "approved" means). Checked after every document upload (`DriverDocumentsService.upload()`). `actorId` is `null` on the audit log row for an auto-approval (action `driver.auto_approve_dev`) vs the admin's id for a real one. Off by default, every use logged as a warning, never set on a server real drivers reach. Verified end to end with a script driving the real HTTP endpoints (apply, upload 4 documents + vehicle_registration, confirm `status` flips to `approved` with zero admin calls, then confirm `POST drivers/me/online` succeeds).

- **Accounts milestone (2026-09-21, all verified on real Supabase):**
  - Approval requires documents: default `cnic_front, cnic_back, license_front, selfie` + `vehicle_registration` per vehicle, overridable with `DRIVER_REQUIRED_DOCUMENTS`. `GET drivers/me` returns `missingDocuments`; admin approve of a driver or vehicle returns 400 with the missing list.

## Bidding / InDrive-style matching (2026-09-22, client requirement change)
The client asked for InDrive + Uber + Careem features combined: passenger-set (negotiable) pricing, requests broadcast to every available driver (not just the nearest few), and a way to browse any location's driver density on the map (not only the caller's own position). Built as a config-switchable mode alongside the original fixed-price flow, per the integration-first principle - nothing about the old Uber/Careem model was removed.

- **`RIDE_PRICING_MODE`** (env, default `bidding`): `bidding` = new InDrive-style flow below; `fixed` = the original flow, byte-for-byte unchanged (`POST rides/:id/accept` still works, `fare` stays null until completion, matching stays "nearest N").
- **Bidding flow:** `POST rides` accepts an optional `offeredFare` (defaults to the fare-table suggestion, `estimate.fare`) and creates the ride with `negotiable: true`. It broadcasts to **every online, approved, not-busy driver of that category** within `NEGOTIABLE_RADIUS_METERS` (default 50 km, i.e. "the whole city"), up to `NEGOTIABLE_OFFERS_LIMIT` (default 300) - not the nearest 5. A driver answers with `POST rides/:id/bid {amount}` (their own price, or the suggested one again to accept it as it stood); `POST rides/:id/accept` is refused on a negotiable ride (409). The passenger watches offers arrive with `GET rides/:id/bids` (also pushed live over the socket as `ride:bid`) and picks one with `POST rides/:id/choose {offerId}` - that sets `ride.fare` immediately to the agreed amount and closes every other offer (`ride:offer_closed`, reused from the existing accept flow). The agreed fare is **not** recalculated from distance driven at completion (that recalculation only happens for `fixed`-mode rides).
- **`RideOffer`** gained `bidAmount` (null until the driver answers) and two new `OfferStatus` values: `bid` (answered, waiting for the passenger) and `closed` (someone else was chosen). `Ride` gained `offeredFare` and `negotiable`.
- **Nearby drivers by any location:** `GET drivers/nearby?lat&lng&radiusMeters&category` (any signed-in user, not role-restricted) - for the Home map to show driver density at a place the person is looking at, not only where they are standing (e.g. sitting in Islamabad, checking Lahore). Returns only `{lat, lng, category, heading}`, no driver identity, since nobody is assigned to anything yet.
- Verified live against Supabase: full bidding flow (broadcast to 3 drivers, one counters, one accepts as suggested, one stays silent and shows as "pending" at the suggested price, passenger picks the counter-offer, losers' offers close, lifecycle to completion keeps the agreed fare, earnings recorded at that fare) and a regression pass confirming `RIDE_PRICING_MODE=fixed` still behaves exactly as before.
- **While still waiting (2026-09-22):** `POST rides/:id/offer {amount?, autoAccept?}` lets the passenger raise/lower the price or flip auto-accept without cancelling; drivers who have not answered yet are pushed a fresh `ride:offer` with the new price. `autoAccept` (set at request time or via that same endpoint) chooses the **first bid at or below the asking price** immediately, reusing `choose()`'s transaction (a losing race there just leaves the bid standing for the passenger to pick by hand). `Ride.autoAccept` (default false). Verified live: mid-wait price change reaches an already-offered driver, an over-budget bid does not auto-accept, an at-or-under-budget bid does.
- **Not built yet:** the Flutter side (editable price on request, an Offers list screen, a driver "send your price" UI, Home map browsing by searched location) - backend is ready for it.

## Driver destination mode (2026-10-08, user decision: Uber "destination filter" / Careem "Go Home")
A driver heading somewhere (e.g. back to Islamabad from Murree) sets a destination; while it is on, matching only offers rides and freight that take them that way.
- Table `driver_destinations` (one row per driver, migration `20261008090000_driver_destination`): place, `active`, `expiresAt`, and the day's use count (`usesDay` = start of the business day, `usesCount`). Separate from `driver_presence` so it can be set while offline.
- `GET/POST/DELETE drivers/me/destination` (driver role, `DestinationService` in `src/presence/`): POST `{lat, lng, address}` turns it on for `DESTINATION_HOURS` (3) and counts a use (moving the place while on is not a new use); at most `DESTINATION_USES_PER_DAY` (2) per business day, else 409. GET also returns `usesLeftToday`, `usesPerDay` and `lastPlace` (to offer it again).
- Switches off by itself: after the hours, or when a position update (`PresenceService.updateLocation`, REST and socket) arrives within `DESTINATION_ARRIVED_METERS` (2 km) - emits `driver.destination_reached`, pushed as `driver:destination_reached`.
- The rule (`src/presence/destination-rule.ts`, unit-tested with Murree/Islamabad points): the drop-off must end nearer the destination than the driver is now, and either within 5 km of it or covering at least 30% of the way; and driver -> pickup -> drop-off -> destination must be at most 1.5x the direct distance + 3 km. Straight-line distances. Applied in `MatchingService.offerRide` (rides, freight, bidding broadcasts and re-broadcasts alike).

## Wallet (2026-10-10, user said "professional implementation, apne tareeqe se")
Careem Pay / inDrive / Bykea style. Module `src/wallet/` (`WalletService`, `AdminWalletService`, `wallet-rules.ts` + spec), migration `20261010090000_wallet`.
- Tables: `wallets` (one balance per user, whole PKR), `wallet_transactions` (append-only ledger, signed amounts, `balanceAfter`, unique `key` per business event, e.g. `ride:<id>:commission`, `request:<id>:credit`), `wallet_requests` (top-ups and withdrawals waiting for an admin), `wallet_settings` (single row id 1, admin-editable).
- `WalletService.post(tx, posting)`: idempotent (insert with skipDuplicates, a repeat key changes nothing), balance moved by one conditional `UPDATE ... RETURNING`, so concurrent postings cannot overspend. Only drivers' postings may go negative (commission, change, ride earnings). Never edit or delete ledger rows; correct with an opposite entry (admin `adjust`).
- Rides: `POST rides` takes `paymentMethod: cash|wallet` (wallet needs `walletPaymentsEnabled` and a positive balance). On completion, inside the same transaction: wallet part = min(fare, balance) moves passenger -> driver, the rest is cash; commission = `commissionPercent` of the fare is taken from the driver's wallet (negative `commission` entry also written to `driver_earnings`, so earnings are net). `rides.walletPaid` and `rides.commission` are stored; the ride view has `payment: {walletPaid, cash}` once completed.
- Free rides (2026-10-13, user decision): a driver's first `freeRidesPerDriver` (default 10, admin setting, 0 = off) completed trips, rides and freight together, carry no commission (`isFreeRide` in `wallet-rules.ts`, counted in `settleRide`). `GET wallet` returns `freeRidesLeft` and `commissionPercent`. Drivers who already have that many trips pay from their next one.
- Dues: a driver below `driverMinBalance` (default -500) cannot go online (403 `WALLET_DUES` with `duesToClear`) and `MatchingService.offerRide` skips them.
- Change: `POST wallet/change {rideId, amount}` (driver, completed ride, within 2 h, once per ride, at most `maxChange`): driver -> passenger.
- Top-up (manual for now): user pays FAZL's account (`topupInstructions` shown in the app), then `POST wallet/topups {amount, method, reference, proofKey?}` (screenshot via `POST wallet/proof`). Same method+reference cannot be used twice. Admin approves (credit) or rejects. A gateway later = a new adapter that credits through the same `post()`.
- Withdrawal (driver only): `POST wallet/withdrawals`; the amount is held at once, released on reject/cancel, stays out on approve (admin pays manually and may add the payout reference). Minimum `minWithdrawal`.
- Max 3 pending requests per kind per user. New requests create an admin notification (`targetType: wallet_request`).
- User routes: `GET wallet`, `GET wallet/transactions`, `GET wallet/requests`, `POST wallet/requests/:id/cancel`. Admin: `GET admin/wallet/overview`, `PUT admin/wallet/settings`, `GET admin/wallet/requests`, `POST admin/wallet/requests/:id/approve|reject`, `GET admin/wallet/wallets`, `GET admin/wallet/wallets/:userId`, `POST admin/wallet/wallets/:userId/adjust`. All admin actions are audited.
- Realtime: `wallet.changed` domain event -> socket `wallet:update {balance}` to that user.
